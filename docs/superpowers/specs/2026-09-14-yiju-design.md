## 一、背景与目标

做一款移动端产品，让用户用一句自然语言描述想学的东西，产品即刻造出一个**真正好玩**的小游戏给他玩。游戏在 App 内的独立页面容器中全屏运行；玩完一局，产品记住用户卡在哪里，据此决定下一局生成什么。

产品要同时解决四件事：

1. 游戏在 App 内独立容器中全屏运行，沉浸、不丢进度、用户感觉不到等待
2. 游戏结合目标学科与学习层次（如数学 · 小学五年级），但**层次不由用户回答**，由目标反推
3. 游戏必须真的好玩——不能是"选择题 + 积分"的换皮
4. 游戏可分享，App 内有社区；社区的核心对象是**作品与二创血缘**

**本次交付物**（均为静态，不含真实后端与真实 AI 调用）：

1. 设计文档：本文件
2. 产品文档：`gamelearn/PRD.md`
3. 可点击原型：`gamelearn/index.html`（单文件，390×844 手机画布）

| 决策点 | 定案 | 理由 |
|--------|------|------|
| 交付形态 | PRD + 静态 demo 页，延续仓库既有模式 | 与 `lull` / `resona` 一致，不引入构建链 |

## 三、定位

**产品名**：「一局」（暂定，备选「起手」「拈来」）

**一句话**：你说想学什么，它给你造一个游戏。玩完一局，它知道下一局该给你什么。

**它不是什么**：不是题库、不是课程平台、不是刷题 App。用户在这个产品里的核心动作是**玩**和**造**，"学"是这两件事的副产品，而且是被设计出来的副产品。

**魔法时刻**：用户说出一句话，几十秒后一个完整可玩的游戏出现在屏幕上，而且它看起来不像作业。

## 四、核心循环

```
① 说目标                 ② 得到一局游戏              ③ 玩完 → 反哺
┌──────────────┐   ┌────────────────────┐   ┌────────────────┐
│ "我想能弹唱   │   │ 机制库选型          │   │ 结算：过了什么、 │
│   一首歌"     │ → │ ＋学科内容填充       │ → │ 卡在哪里        │
│              │   │ ＋难度标定           │   │       ↓        │
│ （对话式）     │   │ （全屏容器打开）      │   │ 影响下一局生成   │
└──────────────┘   └────────────────────┘   └────────────────┘
                                                      │
                                              轨迹累积到目标下
```

循环的每一环都必须成立，缺一环产品就退化成"玩具生成器"：

- ① 不成立 → 用户不知道该说什么（空白页问题）
- ② 不成立 → 生成的东西不好玩，产品当场死亡
- ③ 不成立 → 用户感觉不到进步，没有回来的理由

## 五、"足够好玩"的四条生成律

这是本设计最核心的约束。每生成一局，AI 必须过这四关，不达标不进容器。

| # | 生成律 | 验收问法 |
|---|--------|---------|
| 1 | **玩法先于知识** | 把知识内容全部抽掉，这个机制还让人想玩吗？ |
| 2 | **知识是操作，不是题目** | 知识有没有变成手上的动作——你要砍的那个数、你要搭的那块砖——而不是读完题点一下 |
| 3 | **失败是玩法的一部分** | 答错有没有改变游戏世界（敌人前进、地形塌陷、城墙掉血），而不是弹出"答错啦，正确答案是…" |
| 4 | **一局短且有尽头** | 60–120 秒打完，有明确胜负，结束时有"再来一局"的冲动 |

**第 1 条是对"选择题积分"的死刑判决**：把知识抽掉之后什么都不剩的机制，一律不可用。第 4 条决定手游化节奏——一局短，才能"再来一局"，才有留存。

## 六、生成引擎

### 6.1 机制库（人做） × 学科适配（AI 做）

机制库里的每个机制不是"一个游戏"，而是一份**契约**，声明自己能承载什么形状的知识。

| 机制 | 知识怎么变成操作 | 知识形状 | 跨学科例子 |
|------|----------------|---------|-----------|
| **对撞**（塔防/弹幕） | 打出正确的值才能击碎敌人 | 唯一答案的计算 | 通分、单位换算、音符时值、汇率 |
| **筛选**（贪吃蛇/收集） | 吃掉属于某类的东西，避开不属于的 | 归类判断 | 词性、音程辨认、健康食物、可回收物 |
| **搭路**（平台跳跃） | 每一步落点由自己的选择决定，选错就掉下去 | 序列与顺序 | 语法语序、和弦进行、解题步骤排序 |
| **抢拍**（节奏/反应） | 在正确时机做正确动作 | 时序与反应 | 节奏型、听力辨音、单词重音 |
| **组合**（拼装/建造） | 把零件按规则拼成目标物 | 结构组合 | 化学配平、句子结构、配方比例 |
| **Boss 战**（多阶段） | 综合运用，逐阶段加压 | 综合应用 | 阶段性总复习、曲目完整演奏 |

每个机制声明三样东西，AI 就在这三样范围内自由发挥：

- **难度旋钮**：速度、容错次数、干扰项密度、提示强度、波次
- **知识插槽**：该机制能接受哪些形状的知识（上表第 3 列）
- **皮肤层**：太空 / 海洋 / 夜市 / 森林 / 校园——同一机制换皮肤就是全新的游戏感受

玩法手感由人调好，惊喜来自插槽组合与皮肤。**这是"机制模板 + AI 填内容"落到工程上的样子。**

### 6.2 从"目标"到"游戏"的三级推导

```
① 目标（用户说的）        "我想能弹唱一首歌"
        ↓
② 能力分解（AI 内部）      和弦转换 → 节奏稳定 → 扫弦型 → 完整弹唱
        ↓
③ 知识点 + 难度（AI 内部） 和弦转换 · 入门 · 从 40 BPM 起
        ↓
④ 游戏（用户看到的）       抢拍机制 + 吉他皮肤 + 慢速起手
```

**用户只看到第 ① 层和第 ④ 层，中间两层是 AI 的私事。** 这就是"目标代替层次"落到工程上的样子。

第 ② 层的**能力分解词典**是这个产品真正的资产——它把人类的"学习目标"翻译成机器能调度的知识点。同一句"我想看懂美剧"，英文母语使用者和中文母语者拆出来的能力树完全不同。

demo 阶段这张词典**手工写死**，覆盖 demo 全部目标（2 个深做 + 2 个浅做，见第十一章）。产品化阶段才考虑 AI 生成 + 人工校验。

### 6.3 生成质量的自检回环

```
生成 → 自评四条生成律 → 通过 → 出货
              ↓ 不通过
        换机制重生成（最多 2 次）
              ↓ 仍不通过
        降级到该知识形状的次优机制
```

**兜底保证**：无论 AI 怎么填，用户拿到的一定是"机制合格 + 内容适配"的游戏；最差情况是机制选得不那么惊艳，**永远不会退化成"题干 + 四个选项"**。

### 6.4 等待怎么藏

生成需要时间。产品**不显示"AI 正在生成…"的进度条**，做法是：

1. 先给一句预告（"给你造一个 打僵尸 · 练通分"）
2. 游戏边加载边起播，通用皮肤先顶上
3. 个性化内容在开局前的 3 秒倒计时里注入

**用户永远不等，只感到快。**

## 七、游戏容器契约

"独立页面容器"定义成一份明确接口，容器与游戏之间只通过这些量对话。

**容器 → 游戏**

- 全屏画布
- 统一输入抽象（点 / 拖 / 长按）
- 主题与音效资源
- 系统能力：暂停、退出、结算上报

**游戏 → 容器**

- `attempt`：`{ 知识点标识, 对/错, 耗时 }`
- `finished`：`{ 结局, 总用时, 操作流水 }`

**容器保证三件事**

1. **进入即全屏**，无 App 导航栏，沉浸到底
2. **退出有统一手势**（左上角下滑 + 系统返回），且**中途退出不丢进度**，回来接着打
3. **用户永远不等**（见 6.4）

## 八、目标模型

目标（Goal）是这个产品的中枢对象：它既是层次的载体，又是留存的骨架，又是成长轨迹的容器。

```
目标
├── 用户原话（"我想能弹唱一首歌"）
├── AI 解析出的能力树（用户看不到）
├── 关卡序列（能力节点 → 一局游戏）
├── 成长轨迹（通关记录、卡点变化）
└── 进度（5/12 关）
```

用户来源路径只有一条：**对话创建**。没有表单、没有下拉选年级。

## 九、社区

### 9.1 五个面

底部导航四个 tab：`[ 目标 ] [ 广场 ] [ 排行榜 ] [ 我 ]`。「作品页」与「游戏容器」是详情层，不占 tab。

| 面 | 是 tab 吗 | 内容 | 解决什么 |
|---|---|---|---|
| **目标** | ✔ | 我的目标列表 + 目标详情（关卡序列、成长轨迹），见第八章 | 我回来该干什么 |
| **广场** | ✔ | 作品流（画面 + 标题 + 作者 + 多少人玩过 + 学科标签） | 我不知道玩什么 |
| **排行榜** | ✔ | 三层榜聚合（见 9.3） | 我想知道什么最值得玩 |
| **我** | ✔ | 我造的 / 我改的 / 我玩过的 + 我的战绩 | 我的东西在哪 |
| **作品页** | ✘ | 游戏本体 + 单局榜 + 二创树 + 评论 | 我玩到了好东西，想改它 |

### 9.2 二创树

"改一版"门槛高就没人改，门槛低但改不出花就没意思，因此拆成三档：

| 档位 | 用户做什么 | 门槛 | 学习动作 |
|------|-----------|------|---------|
| **① 换皮** | 一键换主题（太空/海洋/夜市），内容不变 | 一个点击 | 几乎没有，纯爽感 |
| **② 换料** | 保持机制，换学科内容（"通分"→"小数加减"） | 一句话 | **看懂原作的学科逻辑** |
| **③ 改造** | 换机制（贪吃蛇筛选 → 塔防对撞），保留目标 | 一句话 | **看懂原作的机制逻辑 + 迁移** |

**为什么这是学习的核心**：想改，就必须先看懂。这是 Bloom 分类法里最高两层（分析、创造）的动作，比"再玩一局"深得多。而「换皮」这个一键完成的档位是**钩子**——一旦用户换过一次皮，他就不再是纯消费者。

**血缘永不断**：作品页顶部写"改自《分数大作战》· 某某"，底部写"衍生 12 版"。二创不切断署名。原作者的「我」页面能看到衍生数增长，**但不做推送通知**——成就感应来自他自己回来时看到。

### 9.3 排名体系

**技术约束**：每个人的游戏内容是个性化的（同一机制下，你的僵尸是 `3/4 + 1/6`，别人的可能是 `5/8 - 1/4`），成绩无法直接横向比较。因此排名只能建立在**内容对所有人一致**的公开作品上。私人生成的游戏不进任何公共榜。

排行榜 tab 顶部是学科筛选 chips（全部 / 数学 / 英语 / 乐理 / 编程 / 健身…）——"全站最热"对用户没意义，"数学里最热"才有意义。下面三段榜：

**① 作品榜**
- 本周最热：按**玩完率**排，不按点击量（防标题党）
- 最新上架
- 二创之树最大：衍生版本最多的作品

**② 创作者榜**
- 排"本周最会造游戏的人"
- 计分 = 被玩完量 × 被二创数，**不按作品数量**（防刷量刷出一堆垃圾）
- 排的是创造力的产出，不是聪明程度或速度快慢

**③ 我的战绩**
- 我进过的榜、我保持的记录、我离上榜还差多少

**单局榜**（某个公开作品的最高分）留在作品页内，因为它是"这一个游戏"的属性。榜上条目**点一下直接进游戏容器**，不经过作品页，零摩擦。

**周期**：周榜，周一零点重置，新人永远有机会。

**防退化**
- 分层可比：单局榜按机制 × 难度分层，不跨层混排
- 作品榜看玩完率，不只看点击
- 周期制，不形成永久权贵

**定向挑战**：榜是"和所有人比"，挑战是"和你比"。一局打完 →"发给朋友，我 8600 你来试试"。两者共用同一份成绩数据。

**公开与私有：作品怎么进广场和榜**

新造的游戏**默认私有**，只有自己玩得到。结算页给出两个互相独立的动作：

- **「发布到广场」** → 作品进入广场，获得作品页，可被二创，可进榜
- **「发给朋友」** → 只生成一张站外邀请卡，不公开

只有公开作品能进广场、被二创、进任何公共榜。私有作品只在「我」里跟自己比。这条规则同时守住了两件事：用户的默认隐私，以及所有榜单的可比性。

**发布不是不可逆的**：作者可随时把作品撤回私有。撤回后作品从广场与榜上消失，但已产生的二创**保留血缘与署名**（改别人的作品是二创者的劳动，不因原作下架而抹除）。

### 9.4 分享边界

```
站外（微信/任何外部）            站内（App）
┌──────────────────┐          ┌──────────────────┐
│  一位五年级同学     │          │  游戏本体          │
│  邀你挑战          │          │  评论区            │
│  《分数僵尸战》     │  ──→     │  二创树            │
│  【去 App 里玩】    │          │  创作者主页         │
└──────────────────┘          └──────────────────┘
   匿名化：不出现真实姓名、          一切真实互动都在这里
   头像、账号 ID
```

出站卡片用"一位五年级同学""一位吉他初学者"这类身份描述代替真实身份。裂变能力保留，用户的作品与身份不出海。

### 9.5 治理（UGC 四道闸）

泛人群 + 开放社区 = 必须有治理，否则第一次事故就是产品终点。

1. **没有陌生人私信**——从结构上消除骚扰，不靠审核兜
2. **评论先审后发**，举报入口常驻
3. **作品标题与描述过审才能进广场**（未过审只自己可见）
4. **二创不改署名**——血缘由技术保证，不靠自觉

### 9.6 冷启动

demo 阶段广场预置 **12–20 个作品**，覆盖 6 个机制 × 多学科。产品阶段由官方号持续产出机制示范作品，直到自然供给起来。

## 十、数据模型（轻）

| 实体 | 关键字段 |
|------|---------|
| `User` | id、昵称（非实名）、学科偏好 |
| `Goal` | id、user_id、**用户原话**、能力树、进度 |
| `AbilityNode` | goal_id、名称、知识点、难度、顺序 |
| `Mechanic` | id、知识形状、难度旋钮定义、皮肤列表 |
| `Game` | id、mechanic_id、知识点、难度、皮肤、**是否公开**、来源 game_id（二创血缘） |
| `Attempt` | game_id、user_id、逐知识点对错与耗时、结局、用时 |
| `Remix` | 新 game_id、原作 game_id、档位（换皮/换料/改造） |
| `RankingEntry` | 榜类型、周期、对象 id、分数 |

`Game.source_game_id` 是二创树的实现基础：血缘是一棵树，靠这一个字段就能重建。

### 必须真点通的一条主线

```
目标首页
   ▸ 新建目标：说"我想能弹唱一首歌"
       AI 追问 → 预告"给你造一个 手指跑酷 · 练和弦转换" → 进入容器
           ▸ 【真能玩】手指跑酷：和弦落下来，按对指法击碎
               ▸ 结算：过了什么、卡在哪 + 两个动作（发布到广场 ／ 发给朋友）
                   ▸ 【发给朋友】→ 站外邀请卡预览（匿名化）
                   ▸ 目标详情：关卡序列 + 成长轨迹，第 1 关点亮
                       ▸ 广场：自己刚发布的作品已上架
                           ▸ 作品页：单局榜 + 二创树 + 评论
                               ▸ 二创：换皮（一键）→ 换料（一句话）
                                   ▸ 排行榜 tab：作品榜 / 创作者榜 / 我的战绩
```

### 四个目标：2 个深做 + 2 个浅做

深做 = 能走到真游戏容器、真玩、真结算；浅做 = 只有目标卡片与关卡序列，点进去提示"demo 未实现"。浅做的作用是让目标首页看起来像真实产品，而不是一个只有两个条目的样机。

| 目标 | 学科 | 层次表达 | 深度 | 证明什么 |
|------|------|---------|------|---------|
| **能弹唱一首歌** | 乐理 · 兴趣向 | "想能看着谱弹唱" | 深做 | 泛人群：成年兴趣学习者 |
| **搞定五年级通分** | 数学 · K12 | "分数加减老出错" | 深做 | 泛学科：传统 K12 场景 |
| **看懂美剧不用字幕** | 英语 · 兴趣向 | "听力跟不上语速" | 浅做 | 同一机制可换学科内容 |
| **搞懂基金定投** | 财商 · 成人向 | "不想再被割" | 浅做 | 学科可以完全脱离教育语境 |

只做一个目标的话，"各种人群各种学科"就只是文案；两个形态完全不同的目标跑通、另两个只是"差实现"，论点才成立。

### 真能玩的机制：2 个

| 机制 | demo 实现 | 为什么选它 |
|------|----------|-----------|
| **抢拍 / 反应**（手指跑酷） | **真能玩** | 证明"知识是操作"——和弦是指法动作，不是选择题 |
| **对撞**（塔防） | **真能玩** | 证明"失败改变游戏世界"——答错僵尸前进，不弹"答错啦" |
| 筛选 / 搭路 / 组合 / Boss 战 | 静态占位（广场里以卡片出现） | 展示机制库广度，不必都实现 |

## 十二、明确不做（YAGNI）

- 无后端、无数据库
- 无真实 AI 调用：生成过程是剧本化演出，但**节奏按真实延迟设计**（含 6.4 的"用户永远不等"）
- 无账号体系、无登录
- 无真实分享 SDK（邀请卡只做预览）
- 无推送通知
- 无支付
