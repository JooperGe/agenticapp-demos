## 一、产品概述

### 背景与痛点

学习类产品长期只有两种失败形态，各自缺一半：

- **纯题库，无乐趣**：作业帮、猿题库这类产品把知识做成"题干 + 四个选项"。学是学到了，但用户是靠意志力在撑——把知识内容抽掉之后什么都不剩，没有"想再来一局"的冲动。这不是游戏，是测试。
- **纯游戏，无学习**：Roblox、Scratch 这类平台造出来的东西真好玩，但玩什么全凭用户自己，跟"我这周想搞懂的数学"没有关系。乐趣是真的，学习是碰运气。

两种形态之间是一条断层：**用户带着一个具体的学习目标来（"我想能弹唱一首歌""分数加减老出错"），市面上没有一个产品能把这个目标当场变成一个好玩的东西给他玩。** 要么让他去刷题，要么让他自己去游戏平台里摸索。

> 「两种失败形态」是本章的编辑性框架，不是新功能。它概括的正是 spec §三「定位」`:53` 对"题库 / 课程平台 / 刷题 App"的否定，与生成律第 1 条「玩法先于知识」`:87`——把知识抽掉什么都不剩的机制一律不可用。

### 产品定位

**一句话**（spec §三 `:51`）：你说想学什么，它给你造一个游戏。玩完一局，它知道下一局该给你什么。

**它不是什么**（spec §三 `:53`）：不是题库、不是课程平台、不是刷题 App。用户在这个产品里的核心动作是**玩**和**造**，"学"是这两件事的副产品，而且是被设计出来的副产品。

**魔法时刻**（spec §三 `:55`）：用户说出一句话，几十秒后一个完整可玩的游戏出现在屏幕上，而且它看起来不像作业。

**目标用户**：泛人群、泛学科，无角色区分——学生、上班族、退休老人是同一种存在，年级只是层次的一种取值（spec §二「用户范围」`:37`）。

### 三大产品主张

1. **一句成局**——用户只回答"你想干嘛"，不说学科、不说年级、不填表单；层次由 AI 从目标反推，"用户只看到第 ① 层和第 ④ 层，中间两层是 AI 的私事"（spec §二「层次模型」`:38`、§八「目标模型」`:198`、§6.2 三级推导 `:131`）。
2. **好玩优先**——生成的第一约束是"把知识内容全部抽掉，这个机制还让人想玩吗"；好玩度由人的机制库保证，AI 只做内容适配（spec §五 `:81-92`、§6.1 `:117`）。
3. **改就是学**——二创是最深的学习动作，"想改，就必须先看懂"；换皮 / 换料 / 改造三档把门槛压到一个点击或一句话（spec §9.2 `:222-226`）。

## 二、竞品分析

> 本章是 PRD 相对 spec 多出来的那一层：竞品与市场判断，不是产品功能。spec 里 grep 不到任何竞品名。**论据是外部的，结论是 spec §三「定位」的**——本章不借对比塞进任何 spec 没有的功能。

| 类别 | 代表 | 优势 | 对"用户带着目标来"这件事的劣势 |
|---|---|---|---|
| 题库类 | 作业帮 / 猿题库 | 内容贴合考试、见效直接 | 动机靠外部施压；知识即题目，玩不起来 |
| 游戏化刷题类 | 多邻国 | 把坚持做成了机制，学习节奏可控 | 游戏是外壳，内核仍是答对 / 答错；机制与用户想学的内容无关 |
| 创作平台类 | Roblox / Scratch | 创作自由、社区活跃、内容供给强 | 学习目标是用户自己附加的，平台不认目标、也不为学习结果负责 |
| AI 生成游戏类 | 各类 text-to-game demo | 一句话出游戏，生成能力惊艳 | 生成的是"演示"不是"课"：机制随机、难度无标定、玩完不留痕 |

**空白**：没有产品同时做到「机制好玩」与「内容贴合我的目标」。题库类有内容没机制，创作平台类有机制没目标，AI 生成类两样都沾一点、两样都不深。

**结论落在 spec §三「定位」**：

- 「它不是什么」（`:53`）——这一格空白正是不做题库、不做课程平台、不做刷题 App 的理由：这三类各自占住了空白的一侧，再做一个只是重复。
- 「魔法时刻」（`:55`）——真正的差异不在"能生成游戏"，而在"说一句话，几十秒后得到一个完整可玩、且看起来不像作业的游戏"。竞品要么生成得不像课，要么做得像课却不像玩，"不像作业"恰好是没人占住的那一格。

> **不做的事**：本章不引入任何新功能——不写推荐算法、不写 AI 老师、不写成就体系、不写打卡 / 连胜之类的激励。这些在 spec 里都没有出处。

## 三、核心功能设计

### 3.1 目标与对话式创作

**目标（Goal）是产品的中枢对象**：它既是层次的载体，又是留存的骨架，又是成长轨迹的容器（spec §八 `:187`）。首页就是"我的目标"列表，这是 spec §二「产品脊椎」`:42` 说的"目标优先"。

用户来源路径**只有一条：对话创建**——没有表单、没有下拉选年级（spec §八 `:198`）。对话是一句句追问，最后落到一张预告卡：

```
今天想学点什么？ → 用户："我想能弹唱一首歌"
→ "那我们先解决最容易卡住的地方——和弦换手。"
→ "我先想的是一道选择题，想了想那样不好玩——换个机制，让你用手指按和弦。"
→ 预告卡：给你造一个 手指跑酷 · 练和弦转换（抢拍机制 · 一局约 90 秒）→【开始玩】
```

对话里刻意演出了一次"换机制重生成"，对应 spec §6.3 自检回环（`:137-147`）——生成不达标会换机制重来，而不是把"题干 + 四个选项"端给用户。

> 原型实现：`CREATION_SCRIPT`、`startCreation()` / `advanceCreation()`、`renderGoals()`（`gamelearn/index.html:530`、`:703`、`:637`）。

### 3.2 生成引擎

**（a）机制库（人做）× 学科适配（AI 做）。** 机制库里的每个机制不是"一个游戏"，而是一份**契约**，声明自己能承载什么形状的知识（spec §6.1 `:98-117`）：

| 机制 | 知识怎么变成操作 | 知识形状 |
|------|----------------|---------|
| **对撞**（塔防 / 弹幕） | 打出正确的值才能击碎敌人 | 唯一答案的计算 |
| **筛选**（贪吃蛇 / 收集） | 吃掉属于某类的东西，避开不属于的 | 归类判断 |
| **搭路**（平台跳跃） | 每一步落点由自己的选择决定，选错就掉下去 | 序列与顺序 |
| **抢拍**（节奏 / 反应） | 在正确时机做正确动作 | 时序与反应 |
| **组合**（拼装 / 建造） | 把零件按规则拼成目标物 | 结构组合 |
| **Boss 战**（多阶段） | 综合运用，逐阶段加压 | 综合应用 |

每个机制声明三样东西，AI 就在这三样范围内自由发挥（spec `:113-115`）：**难度旋钮**（速度、容错次数、干扰项密度、提示强度、波次）、**知识插槽**（该机制能接受哪些形状的知识）、**皮肤层**（spec 契约给的示例：太空 / 海洋 / 夜市 / 森林 / 校园）。玩法手感由人调好，惊喜来自插槽组合与皮肤。

**（b）从"目标"到"游戏"的三级推导**（spec §6.2 `:119-131`）：

```
① 目标（用户说的）        "我想能弹唱一首歌"
        ↓
② 能力分解（AI 内部）      和弦转换 → 节奏稳定 → 扫弦型 → 完整弹唱
        ↓
③ 知识点 + 难度（AI 内部） 和弦转换 · 入门 · 从 40 BPM 起
        ↓
④ 游戏（用户看到的）       抢拍机制 + 吉他皮肤 + 慢速起手
```

用户只看到第 ① 层和第 ④ 层，中间两层是 AI 的私事——这就是"目标代替层次"落到工程上的样子。第 ② 层的**能力分解词典**是本产品真正的资产（spec `:133`）；demo 阶段手工写死，覆盖全部目标，产品化阶段才考虑 AI 生成 + 人工校验。

**（c）生成质量的自检回环**（spec §6.3 `:137-147`）：生成 → 自评四条生成律 → 通过出货；**不通过换机制重生成（最多 2 次）**，仍不通过则降级到该知识形状的次优机制。兜底保证：无论怎么填，用户拿到的一定是"机制合格 + 内容适配"的游戏，**永远不会退化成"题干 + 四个选项"**。

**（d）等待怎么藏**（spec §6.4 `:149-157`）：不显示"AI 正在生成…"的进度条。做法是三层——先给一句预告（预告条"给你造一个 手指跑酷 · 练和弦转换"）、游戏边加载边起播（骨架屏先顶上）、个性化内容在开局前 **3 秒倒计时**里注入。用户永远不等，只感到快。

> 原型实现：`MECHANICS`（六机制契约）、`GOAL_GAME`、`CREATION_SCRIPT` 的预告卡、`openGame()` → `countdownThenMount()` 的预告条 / 骨架屏 / 3 秒倒计时（`gamelearn/index.html:576`、`:527`、`:536`、`:1067`、`:1083`）。

### 3.3 游戏容器契约

"独立页面容器"被定义成一份明确接口，容器与游戏之间只通过这些量对话（spec §七 `:161-181`）。

**容器 → 游戏**：全屏画布；统一输入抽象（点 / 拖 / 长按）；主题与音效资源；系统能力（暂停、退出、结算上报）。

**游戏 → 容器**：

- `attempt`：`{ 知识点标识, 对/错, 耗时 }`
- `finished`：`{ 结局, 总用时, 操作流水 }`

**容器保证三件事**（spec `:177-181`）：

1. **进入即全屏**——无 App 导航栏，沉浸到底；
2. **退出有统一手势**（左上角下滑 + 系统返回），且**中途退出不丢进度**，回来接着打；
3. **用户永远不等**（见 3.2d）。

> 原型实现：`openGame()` / `mountNow()` / `closeGame()` 管理容器开合；`reportAttempt()` 上报 `attempt`、`finishRun()` 上报 `finished`（`BUS` = 上报总线）；退出走 `.cg-exit` 的左上角下滑手势 + `Esc` 键（`gamelearn/index.html:1067-1115`、`:1350-1366`）。

### 3.4 结算与反哺（核心循环的收尾）

**核心循环有三环，每一环都必须成立——"缺一环产品就退化成『玩具生成器』"**（spec §四 `:59-77`）：

```
① 说目标（对话式）  →  ② 得到一局游戏（机制选型 + 内容填充 + 难度标定，全屏容器打开）  →  ③ 玩完 → 反哺
                                                                                         │
                                                                                  轨迹累积到目标下
```

spec 明写三环各自失败会怎样（`:73-77`）：① 不成立 → 用户不知道该说什么（空白页问题）；② 不成立 → 生成的东西不好玩，产品当场死亡；③ 不成立 → 用户感觉不到进步，没有回来的理由。

**③ 玩完反哺，产品做两件事：**

- **每局结算（per-run）**：按本局各知识点的正确率算出三行——「过了」（正确率高的）、「卡在」（正确率最低的）、「下一关」（把卡点放慢 / 多给机会的反哺文案）。结算**只统计本局的尝试**，不混入上一局。反哺的对象是**知识点，不是分数**：连击 / 命中数一旦上行，就退回成积分式评判——违反的是 spec 对"选择题积分"的死刑判决（spec `:92`），那一条说的正是"积分式评判"这件事。
- **轨迹累积到目标下**：这是 §3.4 的收尾，也是**已经实现**的行为，判据有四条，各自独立：
  1. **赢了才把目标推一格**——`finishRun` 在本局 `outcome === 'win'` 时调用 `advanceGoal(gameId)`，把对应目标的 `done` 推一格；
  2. **输了不动**——「没撑住」不解锁下一项能力，失败是玩法的一部分，不是惩罚也不是进度；
  3. **自造 / 二创的作品不属于任何目标，因而不推进**——`advanceGoal` 先按 `GOAL_GAME` 反查目标，查不到就直接 return；
  4. **到顶不越界**——`done` 不会超过该目标的 `total`。
  累积后如果目标详情页开着会**就地重画**：`done` 推进一格后，那颗「开始这一关」自动往下挪一格。

**结算页给出两个互相独立的动作**（spec §9.3 `:260-267`）：**「发布到广场」** → 作品进入广场、获得作品页、可被二创、可进榜；**「发给朋友」** → 只生成一张站外邀请卡，不公开。新造的游戏**默认私有**，只有公开作品才进广场、被二创、进任何公共榜。

> 原型实现：`finishRun` / `advanceGoal`（核心循环的收尾钩子）、`summarize()` / `showResult()`（结算三行 + 三个动作按钮）、`publishCurrent()` / `shareCurrent()`（`gamelearn/index.html:491-501`、`:1373-1414`、`:1417`、`:1452`）。自检里 `通关会把进度累积回目标` 一条专门验「赢推进 / 输不动 / 自造不推进 / 到顶不越界」（`:2137`）。

### 3.5 社区

底部导航四个 tab：`[ 目标 ] [ 广场 ] [ 排行榜 ] [ 我 ]`；「作品页」与「游戏容器」是详情层，不占 tab（spec §9.1 `:206`）。

**广场**——作品流，每件作品有画面 + 标题 + 作者 + 多少人玩过 + 学科标签（spec `:211`）。解决"我不知道玩什么"。demo 预置 **16 件作品**，其学科标签实际横跨 **8 个学科**（数学 4 / 乐理 4 / 英语 3 / 化学 1 / 语文 1 / 财商 1 / 常识 1 / 健身 1）。

**作品页**（详情层）——游戏本体 + 单局榜 + 二创树 + 评论（spec `:214`）。解决"我玩到了好东西，想改它"。

**二创树——3 个档位**（spec §9.2 `:218-226`）："改一版"门槛高就没人改，门槛低但改不出花就没意思，因此拆成 3 个档位：

| 档位 | 用户做什么 | 门槛 | 学习动作 |
|------|-----------|------|---------|
| **① 换皮** | 一键换主题（demo 实际做出来的 6 个主题：太空 / 深海 / 夜市 / 雨林 / 工坊 / 雪原——与 spec `:115` 皮肤层契约的示例是**两份不同的清单**），内容不变 | 一个点击 | 几乎没有，纯爽感（但它是**钩子**：换过一次皮就不再是纯消费者） |
| **② 换料** | 保持机制，换学科内容（demo 提供**另外 6 个学科**：乐理 / 英语 / 语文 / 化学 / 财商 / 常识——**没有** 数学 / 健身） | 一句话 | 看懂原作的学科逻辑 |
| **③ 改造** | 换机制（筛选 → 对撞），保留目标 | 一句话 | 看懂原作的机制逻辑 + 迁移 |

**血缘永不断**——作品页顶部写"改自《…》· 某某"，底部写"衍生 N 版"；二创不切断署名（spec `:228`）。原作 remixes 计数随之增长，**但不做推送通知**。

**排行榜——3 层榜 + 学科筛选**（spec §9.3 `:230-258`）：

- **技术约束**：每个人的游戏内容是个性化的，成绩无法直接横向比较；因此排名只能建立在**内容对所有人一致**的公开作品上，**私人生成的游戏不进任何公共榜**（spec `:232`）。
- **① 作品榜**：本周最热（按**玩完率**排，不按点击量，防标题党）、最新上架、二创之树最大。
- **② 创作者榜**：计分 = 被玩完量 × 被二创数，**不按作品数量**（防刷量刷出一堆垃圾），排的是创造力的产出、不是聪明程度或速度快慢。
- **③ 我的战绩**：我进过的榜、我保持的记录、我离上榜还差多少。
- 顶部是**学科筛选**，共 **7 个 chips**（「全部」+ 6 个学科：数学 / 乐理 / 英语 / 语文 / 化学 / 财商——**没有** 常识 / 健身）——"全站最热"对用户没意义，"数学里最热"才有意义。
- **周期是周榜，周一零点重置**，新人永远有机会（spec `:251`）。
- **单局榜**（某个公开作品的最高分）留在作品页内，因为它是"这一个游戏"的属性；**单局榜的条目**点一下直接进游戏容器，不经过作品页，零摩擦（spec `:249`）。
- **排行榜页的作品行**则点一下进**作品页**（那里才有二创树 / 单局榜 / 评论）——**两种行的行为不同，别混**：「单局榜条目 → 游戏容器」指的不是排行榜的行。

**发布不是不可逆的**（spec `:269`）：作者可随时把作品撤回私有；撤回后作品从广场与榜上消失，但已产生的二创**保留血缘与署名**。

> 原型实现：`renderSquare()`（广场）、`renderGamePage()` + `chainOf()`（作品页 / 二创树 / 单局榜 / 评论）、`playTarget()`（作品 → 可玩的那一局）+ `.gp-board .board-row` 的点击（单局榜条目直接进容器，spec `:249`）、`startRemix()` / `doRemix()`（三档位，产出物 `parentId` 指向原作、原作 `remixes++`）、`renderRankings()` + `RANK_DEFS` + `RANK_SUBJECTS`（3 层榜 + 学科 chips + 周榜）（`gamelearn/index.html:757`、`:803`、`:792`、`:789`、`:848`、`:861`、`:919`、`:946`）。

### 3.6 分享边界与匿名化

分享单位是**作品 + 可二创**，分享边界是**站内社区 + 站外匿名邀请卡**——裂变与用户隐私兼得（spec §二 `:40-41`、§9.4 `:271-285`）。

```
站外（微信 / 任何外部）            站内（App）
┌──────────────────┐          ┌──────────────────┐
│  一位五年级同学     │          │  游戏本体          │
│  邀你挑战          │          │  评论区            │
│  《分数僵尸战》     │  ──→     │  二创树            │
│  【去 App 里玩】    │          │  创作者主页         │
└──────────────────┘          └──────────────────┘
   匿名化：不出现真实姓名、           一切真实互动都在这里
   头像、账号 ID
```

**匿名化是一条硬约束**，不只是文案：出站卡片上的身份用"一位五年级同学""一位吉他初学者"这类**身份描述**代替真实身份（spec `:285`）。实现上，匿名标签覆盖**全部 8 个学科**（数学 / 乐理 / 英语 / 语文 / 化学 / 财商 / 常识 / 健身）；生成卡片时**只读作品的 title 与 subject，绝不读 author**——卡片上没有昵称的位置，姓名 / 头像 / 账号都留在站内。裂变能力保留，用户的作品与身份不出海。

> 原型实现：`ANON_LABELS`（8 学科匿名标签）、`makeShareCard()` / `shareCurrent()`（只读 title 与 subject）、卡片页脚"卡片上不会出现你的姓名、头像和账号"（`gamelearn/index.html:1432`、`:1439`、`:1452`）。自检里 `卡片上不出现头像或账号 ID` 一条专门验红线（`:2000`）。

### 3.7 治理（UGC 四道闸）

泛人群 + 开放社区 = 必须有治理，否则第一次事故就是产品终点（spec §9.5 `:287-294`）。四道闸：

1. **没有陌生人私信**——从结构上消除骚扰，不靠审核兜；
2. **评论先审后发**，举报入口常驻；
3. **作品标题与描述过审才能进广场**（未过审只自己可见）；
4. **二创不改署名**——血缘由技术保证，不靠自觉。

> 原型实现：作品页有评论区（`renderGamePage` 的 `.gp-comments`），二创产物的血缘由 `parentId` 字段技术保证（`doRemix`）。私信 / 审核后端不在 demo 范围（见第五章）。

### 3.8 「我」页面——"我的东西在哪"

底部导航第四格。它是 spec §9.1 五个面里"**我的东西在哪**"那一格——内容为"我造的 / 我改的 / 我玩过的 + 我的战绩"（spec `:213`）。

**四格统计**：`玩过 / 造过 / 改过 / 最高分`。四格的口径**统一为只统计你自己**（这是"进步只给自己看"在数据上的落法）：

- **玩过** = **本会话打完的局数**（`BUS.runs.length`）。它**不是**"已通关的能力数"——两者单位不同、不可相加；把已通关能力数折进"玩过"，会让赢一局同时推进两处、一局显示成两局。
- **造过** = 你自造、无血缘的作品数；**改过** = 你二创、有血缘的作品数。
- **最高分** = 你名下作品的最高分。

**成长轨迹**：按每个知识点的正确率画条，**从高到低排**。这一页**不排名、不出现人名**——排的是正确率，不是人；与排行榜那种"和所有人比"是两件事。

**我造的**：你名下作品的列表，点开即作品页。

> 原型实现：`myStats()` + `renderMe()`；`myStats().played` 显式注释"不要写成 + GOALS.reduce(...)"（`gamelearn/index.html:1004-1054`）。自检里 `四格统计的数值口径正确，不是一个只数格子的空壳`、`成长轨迹按正确率画条，且不排名` 两条专门验口径（`:2108`、`:2074`）。

## 四、交互与体验原则

### 四条生成律（生成引擎必须过的四关）

这是本设计最核心的约束。每生成一局，AI 必须过这四关，**不达标不进容器**（spec §五 `:81-92`）。名称与验收问法照 spec 原文：

| # | 生成律 | 验收问法 |
|---|--------|---------|
| 1 | **玩法先于知识** | 把知识内容全部抽掉，这个机制还让人想玩吗？ |
| 2 | **知识是操作，不是题目** | 知识有没有变成手上的动作——你要砍的那个数、你要搭的那块砖——而不是读完题点一下？ |
| 3 | **失败是玩法的一部分** | 答错有没有改变游戏世界（敌人前进、地形塌陷、城墙掉血），而不是弹出"答错啦，正确答案是…"？ |
| 4 | **一局短且有尽头** | 60–120 秒打完，有明确胜负，结束时有"再来一局"的冲动？ |

第 1 条是对"选择题积分"的死刑判决；第 4 条决定手游化节奏（spec `:92`）。原型里两条证据：跑酷按错轨道只是掉血断连击、不弹答案；僵尸战答错僵尸前进、城墙裂开，不揭示正确答案。

### 不打扰原则

- **无推送通知**（spec §十二 `:376`）；
- **无陌生人私信**——从结构上消除骚扰（spec §9.5 `:291`）；
- 成就感应来自用户自己回来时看到，而不是被打扰（spec §9.2 `:228`）。

### 进步只给自己看

- 用户**看得见进步，但不打分、不给外人看**（spec §二 `:39`）；
- 排行榜排的是**创造力**（被玩完量 × 被二创数），不是聪明程度或速度快慢（spec §9.3 `:244`）；
- 私人生成的游戏不进任何公共榜；「我」页面的四格只统计你自己、成长轨迹不排名不出现人名（见 3.4 / 3.8）。

## 五、技术形态与 Demo 说明

### 交付物

**一件单文件原型**：`gamelearn/index.html`。390×844 手机画布，内联 CSS 与 JS，**无构建、无依赖、无 CDN、无外部字体与图片**；设计系统是 emoji + CSS 渐变。双击即可在浏览器打开，无需任何安装。

> 说明：spec 第十一章的目录树里列了一个 `gamelearn/assets/`。按 Global Constraints 的依赖禁令，**该目录故意不存在**——设计系统是 emoji + CSS 渐变，没有外部字体 / 图片要放，所以交付物就是这一个单文件。这是对 spec 目录树的一处有意偏离，以本 PRD 与原型为准。

### `?selftest=1` 自检协议

原型内置一套自检探针（**交付时 58 条**，`grep -c "^test(" gamelearn/index.html`）。在 URL 后加 `?selftest=1` 即进入自检模式：探针逐条跑完，全绿时页面 `<title>` 变成 `SELFTEST OK`，任一条失败则变成 `SELFTEST FAIL: <用例名>: <原因>`（在第一条失败处停止报告）。

自检模式会绕过所有需要真实时间的演出（打字、3 秒倒计时、rAF 循环），改走 `mountNow()` 直接挂载，因此可离线、可重复、可无人值守地跑。

### headless 验收命令

```bash
EDGE="/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge"
"$EDGE" --headless --disable-gpu --no-sandbox --virtual-time-budget=4000 \
  --dump-dom "file://$PWD/gamelearn/index.html?selftest=1" 2>/dev/null \
  | grep -o '<title>[^<]*</title>'
```

全绿时输出：

```
<title>SELFTEST OK</title>
```

### demo 做与不做

**做**：

- **4 个目标**，总关卡 6 / 6 / 5 / 4；其中 **2 个深做**（能走到真游戏容器、真玩、真结算）、**2 个浅做**（只有目标卡片与关卡序列，点进去提示"demo 未实现"）。浅做的作用是让目标首页看起来像真实产品，而不是一个只有两个条目的样机（spec §十一 `:347-358`）。
- **6 个机制**——但**只有 2 个真能玩**：**对撞**（分数僵尸战）与**抢拍**（手指跑酷），分别用来证明"失败改变游戏世界"与"知识是操作"（spec §十一 `:360-366`）；另外 4 个（筛选 / 搭路 / 组合 / Boss 战）是机制库契约，在广场里以卡片出现。
- **16 件预置作品**（spec 冷启动要求 12–20 件，交付 16 件），覆盖 6 个机制 × 多学科。
- 一条真点得通的主线：目标 → 对话 → 预告 → 容器（真玩）→ 结算 → 发布 / 分享 → 目标详情点亮 → 广场 → 作品页 → 二创（换皮 / 换料）→ 排行榜。

**不做**（spec §十二 YAGNI `:370-377`）：

- 无后端、无数据库；
- 无真实 AI 调用——生成过程是**剧本化演出**，但节奏按真实延迟设计（含"用户永远不等"）；
- 无账号体系、无登录；
- **无陌生人私信**——从结构上就不存在这个通道，不是"先不做"（见 3.7 治理第一闸）；
- 无真实分享 SDK（邀请卡只做预览）；
- 无推送通知；
- 无支付。

### 「2 个机制可玩」的后果（必须写清）

**16 件预置作品里，有 9 件点名的是 demo 做不出来的机制**——`collect` 3 + `path` 2 + `build` 2 + `boss` 2。这些作品在广场里正常展示卡片与标签，但**点「游玩」会回落到抢拍**（走当前可玩的机制之一），不会按卡片上的机制标签运行。换句话说：**只有 4 件 `collide` + 3 件 `rhythm` 共 7 件能按自己的机制真玩**。

只写"6 机制 2 可玩"会让读者以为 16 件都能按标签玩——这是必须补上的后果。

## 附：名词

- **机制（Mechanic）**：人能玩的一份契约，声明它接受什么形状的知识、有哪些难度旋钮与皮肤。
- **知识形状**：机制能承载的知识的形态（唯一答案的计算 / 归类判断 / 序列与顺序 / 时序与反应 / 结构组合 / 综合应用）。
- **目标（Goal）**：用户原话 + AI 解析出的能力树 + 关卡序列 + 成长轨迹 + 进度。
- **二创血缘**：二创产物通过一个指向原作的字段建立血缘（spec §十 `:315` 的数据模型里叫 `Game.source_game_id`，原型里叫 `parentId`）。血缘是一棵树，靠这一个字段就能重建。
